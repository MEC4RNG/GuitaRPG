# TAX-001 — Canonical Musical Taxonomy Contract

**Status:** COMPLETE  
**Date:** 2026-09-27  
**Authority:** Phase 0 — Architecture & Contracts

## Objective

Replace the prototype's overlapping category model with one canonical musical vocabulary suitable for Quest generation, progression, Codex content, recommendations, and history.

## Result

Accepted canonical model:

- Domain
- Skill
- Concept
- Context
- Constraint Definition
- Attribute
- Tag
- Relationship

### Key normalization

Technique is not stored as a duplicate parallel entity type.

Trainable techniques such as Alternate Picking, Sweep Picking, Bending, Vibrato, and Hybrid Picking are canonical Skills. A Quest may use the same Skill in the role `REQUIRED_TECHNIQUE` without creating a second entity.

This preserves the earlier product requirement that one canonical entity may serve different Quest roles.

### Canonical Domains

1. Technique
2. Fretboard
3. Harmony & Theory
4. Rhythm
5. Ear & Musicianship
6. Creativity & Expression

### Semantic separation

- Skill = trainable capability
- Concept = musical material/idea
- Context = musical environment
- Constraint = imposed restriction
- Attribute = derived Character dimension
- Tag = metadata only

Player proficiency attaches to Skills, not Concepts, Contexts, Constraints, Tags, or Attributes.

## Legacy impact

The existing `challenge.js` was inspected as source material. It currently mixes semantic layers across `guitarmanship`, picking/fretting hand, string challenges, musicianship, scales, rhythm, styles, and selectable attributes.

TAX-001 does not alter or discard that content. TAX-002 must explicitly account for every legacy value.
