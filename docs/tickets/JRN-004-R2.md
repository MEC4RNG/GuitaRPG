## 1. Problem and agreed end-state

Existing JRN-004/R1 preserves Player-owned Workbook persistence, Quest/stage links, reusable tab/chord editing, and Explore module ordering. The user confirms these functions but does NOT accept the current layout. The Quest screen repeats metadata, puts Map Workbooks ahead of learning content, duplicates Practice controls, and presents a cluttered embedded Craft editor. Map is a collection of static tabs instead of a responsive bridge from Quest objectives to learning and personal work.

**Target workflow:** Quest title and concise status/context → selectable objective/challenge items → Map displays source-grounded information for the selection → explicit **New Workbook** creates one owned, reference-seeded Page 1 → player is taken to **Explore**, relevant module expanded, page open for editing. Map keeps existing Workbook discovery in the right sidebar; shared **Start Practice** lives in the Quest header. Craft retains a composition-first editor with the right-side Quest Toolkit and cleaned-up controls.

Do not redefine the immutable Quest, Stage lifecycle, Session, Result, Difficulty, evidence, or progression authority.

## 2. Primary information architecture

### 2.1 Header and Quest card

- Remove the redundant `{quest.identity.type} QUEST JOURNEY` eyebrow (e.g. “Exploration Quest Journey”) in `components/quest-journey-surface.tsx`.
- Show the canonical Quest title with its immutable objective summary as the primary hierarchy, with visually separated but readable objective/challenge selections. A compelling illustrative title/objective divider is a **future design task**, NOT a prerequisite or authorized image asset in R2.
- Consolidate Status, Demand, Suggested Session, Working Stage and Primary Skill into a compact **Quest-header** values/chip strip. Avoid five large repeated label cards; keep precise accessible names (`aria-label` / visually hidden text or concise visible labels where needed), tooltips only as supplementary text, and existing lifecycle semantics. Stage selection remains obvious in Map/Explore/Craft navigator. Do not rely on color alone.
- Different semantic colors for metadata may be designed later; R2 may use existing tokens for restrained emphasis, but must not invent a permanent semantic color taxonomy.
- Use the reclaimed main Quest-information area for **actual snapshot-derived challenges and requirements**: primary/supporting Skills, required Techniques, Concepts, Context, selected constraints and parameters, typed objective criteria and their units/thresholds where applicable. Present readable text labels on desktop AND mobile for now; icons-only navigation is deferred.
- Items must remain individually legible with long names, many constraints, and narrow viewports; no accidental duplicate requirements in an expanded footer. Values must come from the immutable snapshot. Do not invent objectives, skill-specific tasks or requirements.
- Link official canonical references via existing `questCodexReferences` / Codex Peek ONLY when a real matching entry exists. Numeric targets, restrictions and unsupported criteria remain descriptive but not falsely linked.

### 2.2 Objective/parameter selection

- A selectable item has stable UI identity and type, e.g. primary Skill, secondary Skill, required Technique, Concept, Context, Constraint or Objective criterion; do not force criteria into taxonomy slugs.
- Selecting an item updates the corresponding **Map information regions** using presentation state, without editing Quest/Result data or starting Practice. If the user invokes a selectable header item from Explore/Craft, intentionally switch to Map and select it (respect existing Journey stage/lifecycle guards); no hidden stage changes from passive browsing.
- Provide keyboard-operable selectors with selected/focus state and usable touch targets. Long-form objective summary remains visible as the Quest's purpose even when another parameter is selected.

### 2.3 Map main detail regions

Replace the static Map category tabs as the principal learning UI with an objective-driven detail panel. Provide consistent regions, rendering only grounded content:

1. **What it is** — selected term, canonical Codex definition, metadata/relationships where available; clear source attribution and link to Codex Peek / full entry.
2. **Within this Quest** — actual role, objective criterion, Context, numeric threshold, constraint/restriction, or requirement from the immutable Quest snapshot.
3. **How to explore it** — existing authored examples/exercise guidance ONLY when present; otherwise concise truthful fallback (no AI-generated explanation presented as official content).
4. **Workbook action area** — clear **New Workbook** tied to the selected topic, with status/errors.

The selected topic should remain visible and accessible. Existing Codex Peek must continue preserving page draft/focus state. Constraints may have an official CONSTRAINT Codex entry, but individual restrictive values still need their exact literal meaning. No misleading full course content for sparse entries.

**Important boundary:** Existing `CODEX_CONTENT_V1` is definition-oriented. Large-scale official Codex enrichment (diagrams, worked examples, curriculum, new schema) is a **separately proposed content workstream**, not a blocker for the R2 UI. `JRN-005` concerns owner-scoped *personal* notes discovery and remains unauthorized. Do not silently introduce either expansion.

## 3. Map → New Workbook → Explore vertical slice

### 3.1 One explicit, recoverable create action

- The visible **New Workbook** action must actually create a **new Player-owned Workbook** (not an implicit Quick Note), with an initial Page 1 populated from the selected Quest objective/challenge and any verified Codex definition/reference available. Also include a clear editable “My notes / observations” area.
- Prefer existing `GUITARPG_WORKBOOK_DOCUMENT_V1` heading/paragraph/list blocks, bounded validation, and existing `create_player_workbook_v1` creation route where supported; no new document format, raw HTML authority, or new imported Codex content store. Seed content is a **snapshot** with source kind/slug/name and current `CODEX_CONTENT_V1` version as human-readable provenance; official text and user-written edits must be clearly distinguished. The original Codex remains authoritative; later official revisions do not silently overwrite the Player page.
- Set meaningful, bounded Workbook/Page titles, preserve page ordering and accepted revisions, and do not fabricate lesson content. Empty/noncanonical criteria yield truthful Quest-specific facts and editable notes, not an imaginary Codex entry.
- Ensure duplicate-click protection, retry behavior, and truthful partial-failure recovery. Do not assume the existing creation RPC's request ID already guarantees exactly-once creation without verifying the contract. If an atomic/idempotent operation is required, propose the narrowest authorized addition and security tests. If a request may have committed before a network failure, resolve outcome rather than blindly creating a second Workbook.

### 3.2 Linking and handoff semantics

- Link the created Page to the *owned* current Quest using existing trusted context operations; include Map reference context for sidebar discovery where applicable.
- When the selected item maps to a genuine Explore module (canonical Quest primary/secondary/required-technique Skill), explicitly associate the new Page with that module via the JRN-004-R1 trusted `module_key` boundary. For a Concept/Context/Constraint/criterion without a valid module, preserve a general/unassigned Explore association; never guess a Skill using title or fuzzy matching.
- Do not call “linked” until server acceptance. Partial failures must preserve the owned Workbook/Page and surface a clear **retry association** path; no unintended Page deletion and no false save/completion status.
- On successful creation, move the Journey intentionally to **Explore**, expand the appropriate Skill module (or General/Unassigned section), select the created Page, and display the **actual editable Workbook content inline** rather than redirecting out to `/workbooks`. Make target module and page identification deterministic and safe across async hydration; avoid untrusted arbitrary URLs/query redirection.
- Reuse the same owner-scoped document parser, editor components, Supabase repository, trusted mutation paths, autosave/concurrency, and revision state used by standalone Workbooks and Craft. **Do not create a second editor/document store or mount simultaneous editors for one Page.**
- Protect pending/unsaved/conflicting edits when switching modules, pages, stages, or opening full editor. If the handoff stage change fails, do not lose or orphan the Page; present a safe path back to the created Workbook.
- Existing Explore module ordering, collapsible modules, legacy unassigned pages and cross-device rehydration remain intact. User can reopen a previously linked Workbook from Explore and from standalone `/workbooks`.

## 4. Sidebar and Start Practice

- **Map:** Remove the generic top-of-main-canvas “Notes and references”/Workbook section. Move Quest-linked Workbook list and Open/Create/Link affordances to the existing **right-hand aside** formerly labeled **Practice This Journey**. Keep distinguishable page names, owning Workbook/context and empty states; do not imply a link to the selected objective unless an explicit association actually exists. Quest-wide links may include Map and Explore pages as appropriate.
- **Explore:** Main canvas remains modular, now with one selected module's inline Workbook editor as appropriate. Do not add a duplicate full Workbook navigation list beside every module; default to more main-canvas width if the sidebar has no distinct useful function.
- **Craft:** Retain the previously agreed **Quest Toolkit** on the right, with Skills, Techniques, Context/constraints and creative prompts. Do not remove core reference information to move the button.
- **All three stages:** Relocate `Start Practice`/`Practice Again` into a shared, visible **Quest-header action**, rather than a large stage sidebar. This is the default R2 implementation choice; only introduce a small mobile sticky variant if actual responsive testing demonstrates a need. Do **not** build a floating overlay by default (could obscure tab, chord controls, keyboard focus). Preserve `Start Quest`, restore/reopen/archival guards and session behavior as distinct actions. Start Practice alone creates a Session; simple content interaction does not.
- If the header's main Quest card becomes too tall on mobile, allow wrapping or compact semantic labels, not arbitrary hiding of requirements.

## 5. Craft editor usability and site-copy reduction

- **Pointer defect:** The user reports a noninteractive-looking mouse cursor over Craft composition controls. Reproduce/inspect first: the current CSS cursor rule on `.workbook-library button:not(:disabled)` does not inherently apply to `.craft-workspace`. Fix enabled buttons, selectors, page selectors and page menus with clear pointer, hover, focus, touch and disabled affordances; verify with actual browser tests, not CSS-only assertions.
- **Spacing:** Improve grouping and breathing room around composition header/actions, selector, toolbar, page controls and editor canvas, without increasing screen-height noise.
- **Confusing left/navigation area:** The embedded Craft outer composition chooser plus inner `WorkbookEditorPrototype` navigation presents overlapping page hierarchies. Create **one primary composition selector/active-page indicator** and contextual controls; show actual Workbook ownership. An embedded/presentation variant may hide redundant *chrome* without removing page operations, save status, revision safety or the full standalone editor's features.
- Reduce redundant headings, footers, explanatory text and repetitive labels **within the Quest Journey and embedded editor**. Retain required save/conflict/offline/error/retry feedback, recovery, guest privacy, archived state, non-grading truthfulness and semantic accessibility. Global site-wide cleanup outside the affected surfaces is a separate future UX/design-system ticket.
- Craft still defaults to most recently edited owned/unarchived Quest-linked CRAFT page, supports multiple pages, and never overwrites unsaved changes on navigation.

## 6. Non-negotiable invariants and excluded work

1. Canonical Quest snapshot, immutable objectives/criteria, declared difficulty and Journey lifecycle remain authoritative. UI selection and Workbook editing are not evidence, Session time, Result or XP.
2. Workbook → ordered Pages → retained immutable bounded revisions is always Player-owned (`auth.uid()`); Quest/module references are optional association edges only. Deleting a deletable Quest removes links, **not** Workbook content; attempted-Quest deletion guard remains intact.
3. All mutations occur through existing trusted owner-validated RPCs or a narrowly documented equivalent; RLS, grants, guest/protected account boundaries, account deletion and historical revision integrity remain intact.
4. No silent change to `CODEX_CONTENT_V1`, global canonical taxonomy entity associations, JRN-005 “Your notes” discovery, FRET-001, Build Quest, generation, Training, automatic evaluation, performance scoring, PDF/media, or other postponed work.
5. Keep `main`, production and public traffic unchanged. Any database change must be additive, bounded, locally replayed and applied only to the authorized staging project after verification; no rewriting applied migrations.

Deferred visual enhancements: richer official Codex articles/illustrations, the “awesome” title-versus-objectives background graphic, metadata value color language and potential mobile icons, fully general site-wide header/footer pruning, and drag-and-drop reordering.
