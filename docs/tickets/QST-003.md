## Generator version and architecture

The public APIs are `generateQuickQuest(input)` and `generateCustomQuest(input)`.
Both use generator version `QST_GEN_V1` and compatibility rules
`QST_GEN_RULES_V1`. The implementation separates:

1. typed public requests and structured errors
2. source-controlled template-family catalog
3. active canonical taxonomy lookup and catalog validation
4. centralized parameter/constraint bounds
5. seeded selection
6. resolved Quest construction
7. pending-container DIF_V1 evaluation
8. final schema-v1 parsing and QST-002 persistence mapping

The temporary pending difficulty container is internal and is never returned.

## Quick semantics

Quick accepts no required musical configuration. Optional Domain, Quest Type, and
tuning filters narrow the compatible family space. A caller-supplied seed makes the
musical composition reproducible; the convenience path creates a platform UUID seed.
The effective seed is retained in metadata. Selection occurs within coherent families,
not by independently randomizing Skills, Concepts, Contexts, and Constraints.

## Custom semantics and precedence

Custom requires an active, generator-eligible canonical Primary Skill. It can anchor
Quest Type, Concepts, Secondary Skills, Required Techniques, tuning, tonal center,
style, Constraints, duration, tempo, string set, fret range, and meter.

Precedence is explicit valid selection, family hard requirements, compatible defaults,
then seeded compatible selection. Unknown, wrong-kind, duplicate, deprecated,
out-of-family, out-of-bounds, or contradictory selections raise a
`QuestGenerationError` with a stable code; requested content is never silently
substituted.

## Catalog and compatibility model

`QST_GEN_V1` contains six reusable families:

| Family | Domain | Quest Types |
| --- | --- | --- |
| `execution_grid_v1` | Technique | Technique, Performance |
| `fretboard_route_v1` | Fretboard | Exploration, Performance |
| `theory_builder_v1` | Harmony & Theory | Knowledge, Creative |
| `rhythm_lock_v1` | Rhythm | Performance, Technique |
| `ear_prompt_v1` | Ear & Musicianship | Knowledge, Exploration |
| `creative_counterpoint_v1` | Creativity & Expression | Creative |

Every catalog reference is checked against active taxonomy; Primary Skill Domain
membership is derived from canonical `BELONGS_TO` relationships. Each family limits
eligible Skills, Concepts, supporting roles, Quest Types, and Constraints, and every
family is proven instantiable. The 24 Phase 0 fixtures informed these reusable patterns;
the generator does not copy or return fixtures.

## Parameter and constraint rules

Versioned centralized bounds require durations of 1–120 minutes, tempos of 30–240
BPM, frets 0–24 with ordered endpoints, unique guitar strings 1–6, positive bounded
counts, time windows of 5–3600 seconds, and output lengths of 1–64 bars. Quests contain
one to three unique family-compatible Constraints. Named no-parameter Constraints stay
canonical. `single_string_only` rejects a multi-string `string_set`; duplicate or
invalid parameter sources are rejected rather than normalized into different content.

## Identity and provenance

Every instance receives a schema-v1 ID, canonical slug, human title, and origin
`QST_GEN_V1`. Explicit seeds and identity inputs make tests reproducible; production
generation uses a UUID seed when none is supplied. Metadata retains generator version,
rule version, template ID, mode, effective seed/nonce, and only a caller-supplied
generation timestamp. No display text is semantic authority.

## Objective, completion, and verification

Family semantics build structured criteria for sustained practice, position discovery,
construction, identification, or creative output. Resolved duration, tempo, prompt, and
output values flow into criteria. Completion always uses meaningful-attempt semantics
and `mastery_claimed: false`. Identification can recommend APP_VERIFIED; performance
and practice families recommend SESSION while retaining SELF. Audio modes are never
required and are not chosen randomly.

## Difficulty integration and DIF-003 boundary

Construction first creates an internally valid pending candidate, DIF-002 computes the
complete immutable `DIF_V1` profile, and the generator replaces the pending container
before final parsing. The declared Level is always the computed overall Level. DIF-002
mathematics are unchanged.

Player state is not part of either request. The generator does not inspect proficiency,
confidence, readiness, goals, XP, Character Level, challenge preference, or DIF-003.
Personal difficulty remains a separate later Player × Quest snapshot.

## Persistence readiness

Every finalized Quest passes `parseQuest` and `toQuestPersistenceInput`. QST-002's JSONB
difficulty container and resolved snapshot preserve the complete computed profile, so
no migration is needed. There is no application-level atomic multi-table Quest write
adapter in the current repository. That gap does not block QST-003's persistence-ready
domain output and should be handled as a narrow later QST integration ticket rather
than an unapproved RPC or migration.
