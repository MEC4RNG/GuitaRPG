# PLY-002 — Player Profile & Development Persistence

**Status:** COMPLETE
**Phase:** 1 — Product Foundation  
**Date:** 2026-09-28  
**Depends on:** DATA-002, TAX-003, PLY-001, PROG-001

## Objective

Implement the durable Player substrate defined by PLY-001 under the DATA-001 ownership
and security model, without implementing onboarding UX or progression algorithms.

## Implemented persistence layers

Player-authored / owner-controlled:

- `public.player_profiles`
- `public.player_tuning_preferences`
- `public.player_setups`
- `public.player_goals`

Player-derived / system-authoritative:

- `public.player_skill_states`
- `public.player_character_states`
- `public.player_attribute_states`

## New-Player bootstrap

Every Supabase Auth UUID, including anonymous Auth users, receives the same base Player
model through an Auth insert trigger:

- one profile
- Character Level 1
- Practice XP 0
- total recorded practice time 0
- one explicit UNRATED state for each of 72 active canonical Skills
- one explicit UNASSESSED state for each of 11 active canonical Attributes

Self-declared experience does not mutate Skill proficiency.

## Authority boundary

Owner-editable state uses explicit column-level PostgreSQL grants plus RLS.

Clients may not directly mutate:

- Skill proficiency/level/confidence/readiness/exposure
- Practice XP
- Character Level
- total practice time
- Attribute scores
- ownership UUIDs
- system timestamps

Trusted service/server paths retain controlled write authority for future PROG/EVD work.

## Tuning/setup model

Preferred/default tunings reference canonical Context entities.

Skills remain one row per Player × canonical Skill; they are not duplicated by tuning.

Player setups store only minimal v1 guitar metadata:

- label
- broad guitar type
- string count
- optional default tuning Context
- default flag

## Goals

Goals may reference:

- canonical Domain
- canonical Skill
- broader text objective

Goals remain recommendation context only and do not award progression.

## Data integrity

The database enforces:

- PLY-001 enum/state values
- UNRATED null/zero semantics
- ESTABLISHED confidence floor from PROG-001
- visible Level ↔ proficiency-band consistency
- UNASSESSED Attribute null semantics
- canonical taxonomy kind references
- one default tuning per Player
- one default setup per Player
- immutable ownership
- Auth-user hard-delete cascade

## Database security tests

`supabase/tests/database/player_persistence_rls.test.sql` covers:

- RLS enabled
- unauthenticated denial
- owner visibility/edit rights
- non-owner isolation
- cross-owner insert denial
- immutable ownership
- derived-authoritative mutation denial
- anonymous Auth equivalence
- trusted service mutation path
- representative new-Player state
- experience does not grant proficiency
- account-deletion cascade

A dedicated GitHub database workflow runs the migrations and pgTAP suite against a
fresh local Supabase database.

## Non-goals

PLY-002 does not implement:

- login/signup/onboarding UI
- calibration algorithm
- Quest/session/evidence persistence
- XP award algorithm
- proficiency update algorithm
- readiness decay algorithm
- Attribute derivation algorithm
- Character Level threshold curve
- milestone catalog
- recommendation logic
- user-facing export UI
