# JRN-001 — Interactive Workbook Editor Prototype

Status: **AWAITING_USER_INTERACTIVE_REVIEW**

Branch: `jrn-001-workbook-editor-prototype`

Target: `v1-production`
Production cutover: **NOT AUTHORIZED**

## Outcome

JRN-001 implements an isolated, in-memory Workbook Editor prototype at
`/prototype/workbook`. The route is available locally and on non-production Preview deployments;
when `VERCEL_ENV=production`, it resolves through `notFound()` and is not linked from application
navigation. The prototype does not authenticate, call Supabase, persist remotely, or alter Quest,
Journey, Session, Result, Codex, MEC, or progression state.

## Implementation

- `components/workbook-editor-prototype.tsx` — Tiptap editor, temporary pages, toolbar, React
  musical node views, and visible JSON import/export.
- `lib/workbook/document-v1.ts` — typed GuitaRPG-owned document contract, validation, stable block
  identities, tuning snapshots, and bidirectional editor adapters.
- `app/prototype/workbook/page.tsx` — isolated Preview/local route with a production boundary.
- `app/globals.css` — responsive, accessible editor, tablature, chord, toolbar, and page styles.
- `tests/workbook-document-v1.test.ts` — deterministic contract and canonical round-trip coverage.
- `tests/workbook-prototype.test.ts` — isolation and production-boundary coverage.
- `tests/e2e/workbook-prototype.spec.ts` — real interaction, page, import, clipboard, accessibility,
  and narrow-viewport coverage.

## Document contract

The authoritative interchange shape is `GUITARPG_WORKBOOK_DOCUMENT_V1`, schema version 1. Text,
lists, tablature, and chord diagrams have stable block identities. Tablature events also have stable
identities. Standard and DADGAD snapshots use the accepted low-to-high storage order while the UI
renders high-to-low. Malformed blocks without a recoverable identity fail with an announced error.
Unknown identified blocks are retained as read-only unsupported blocks with their original JSON.
Executable pasted HTML is not retained or executed.

## Prototype capability

- Rich text: paragraphs, three heading levels in the schema, bold, italic, bullet and ordered lists.
- Pages: create, select, rename, duplicate with new block/event identities, and delete in memory.
- Tablature: six strings, fret/open/mute/clear, simultaneous notes, add/remove positions, duplicate,
  Standard/DADGAD tuning, arrow-key cell navigation, touch controls, and an accessible summary.
- Chords: six structured strings, name, fret window, fret/open/mute/clear, tuning snapshot schema,
  finger/barre-compatible data, and a generated textual summary.
- History: text and musical node changes use the same ProseMirror transaction history.
- Serialization: visible export/import/reset controls round trip through the owned schema and never
  transmit data.

## JRN-001-R1 usability remediation

Interactive review identified four presentation and interaction gaps in the first prototype. The
rich-text toolbar read Tiptap state only during React renders, browser list-reset styles suppressed
markers, tablature used a fixed four-column CSS template plus a separate confirmation action, and
the chord editor displayed string lines rather than a conventional fret grid.

The remediation keeps the same document contract and replaces those weak interaction surfaces:

- Tiptap's reactive editor-state subscription now keeps Paragraph, Heading, Bold, Italic, Bullets,
  Numbered, Undo, and Redo state synchronized with selection and transactions. Headings have a
  visible hierarchy, while ordered and unordered list markers and indentation are explicitly owned
  by the editor stylesheet.
- New tablature starts with 16 numbered positions in one non-wrapping grid. Additional positions
  extend the internal horizontal scroller. A focused cell accepts direct one- or two-digit fret
  entry; Backspace/Delete clears it, and the mobile numeric field commits valid frets immediately.
  Open, mute, clear, arrows, identity, order, validation, and unified history remain intact.
- Chords now use six vertical strings and five visible horizontal fret spaces. Clicking an
  intersection places the selected absolute fret directly. Open/mute state, string selection,
  starting-fret label, name, tuning, and notes outside the visible window are explicit. Moving the
  window never rewrites stored absolute frets.
- JSON remains visible in the textarea for round-trip inspection. The display action is named
  literally, and a separate local Download JSON file action is available.

No schema, authentication, persistence, production, or public-traffic change is part of R1.

## JRN-001-R2 multi-system and import remediation

The second interactive review found that a single horizontally expanding tablature strip did not
match conventional workbook reading, dense per-position controls competed with the notation, chord
markers needed clearer string alignment, and JSON file import was missing. R2 retains the same
memory-only document authority while refining those surfaces:

- Tablature remains one continuous, identity-preserving event sequence, presented as numbered
  systems of 4, 8, 12, or 16 positions per line (16 by default). Changing presentation density does
  not rewrite events. Placeholder cells materialize only the required contiguous positions, and
  cross-system arrow navigation follows musical order.
- Focused tab cells accept `x` for muted, `0` for open, and direct frets 1–36. Destructive removal
  of a note-bearing position requires an explicit confirmation. Secondary position and block
  actions live in a compact disclosure while adding and removing positions remain readily
  available.
- Musical node views contain editor events so that returning to ordinary text, typing, selecting,
  copying, pasting, or navigating cannot accidentally replace a tablature or chord block. All
  deliberate musical changes remain in unified undo/redo history.
- Chord string lines, markers, open/mute indicators, and controls share conventional six-string
  geometry on desktop and mobile.
- A local JSON file picker complements visible text import/export and download. It accepts JSON
  files up to 1 MiB, validates before replacement, asks for confirmation, preserves the active page
  after empty/malformed/unsupported input, and never uploads content.

No authentication, persistence, database, production, or public-traffic change is part of R2.

## JRN-001-R3 layout, selection-safety, and mobile-editing remediation

The third interactive review found that the desktop Pages sidebar consumed notation width, normal
ProseMirror node selection could still arm an entire musical block for replacement, globally sized
44px buttons made desktop tablature unusually tall, and the mobile fret input was hidden behind a
secondary-action disclosure. R3 preserves the owned document contract while addressing those
interaction defects:

- Pages is now a compact navigation region above the page title and toolbar. The editor is a
  single-column surface, page selectors scroll horizontally without shrinking, and New, Duplicate,
  and Delete remain labeled and keyboard/touch accessible. Browser coverage switches between pages
  after an unsaved edit and verifies that the edit remains on its owning page.
- Tablature and chord nodes were atomic and selectable by default. `stopEvent` correctly contained
  control interactions, but it did not prevent a background pointer event from creating a
  ProseMirror `NodeSelection`; the next ordinary text input could therefore replace the selected
  atom. Both musical node specifications are now non-selectable, and an exact background press
  explicitly returns the editor to the safe adjacent text context. The node view exposes its real
  selected state only for regression evidence; border color is not treated as selection authority.
- Real Chromium keyboard coverage reproduces the reported background-click/ordinary-typing path
  for tablature and chord diagrams, verifies that neither node is selected or replaced, and covers
  inside/outside focus, explicit Return to document, two adjacent musical blocks, text insertion,
  explicit deletion, undo/redo, and the owned JSON representation after editing.
- Desktop fine-pointer tablature cells are 32px high for a denser conventional six-string staff.
  Coarse-pointer devices retain the design-system 44px minimum target, so reducing visual rhythm
  does not reduce touch accuracy, focus visibility, string alignment, or note readability.
- The selected tablature position now has an always-visible contextual numeric fret field directly
  below the notation, with Previous/Next, Open, Mute, and Clear controls alongside it. Selecting a
  cell updates the context; tapping the input provides an explicit `inputmode=numeric` keyboard
  path and valid frets update immediately. Duplicate/Delete remain secondary block actions. Chord
  placement remains direct, while its name and fret-window inputs stay visible.

Pixel 7 Chromium, 320px Chromium, and Mobile WebKit runs are browser emulation, not evidence that a
physical software keyboard opened. They prove the visible tap-to-edit path, focus, value updates,
44px coarse targets, scrolling, axe checks, and lack of horizontal page overflow. Physical-device
keyboard presentation remains part of user interactive review.

The independently observed application-wide mobile-navigation gap is recorded but deliberately not
changed here: the bottom bar exposes Home, Generate, Skills, and Profile while Quests, Training,
Character, Codex, and History lack a general mobile entry point. A separately authorized ticket
should retain those four destinations and add an accessible top-bar menu for all canonical groups.
`MOBILE_NAVIGATION_ITEMS` and the shared application shell are unchanged by JRN-001-R3.

No authentication, persistence, database, production, public-traffic, or shared-navigation change
is part of R3.

## JRN-001-R4 navigation, direct-entry, and viewport remediation

The fourth interactive review found that the horizontal Pages region still presented its heading,
selectors, and actions as separate visual groups; button-based tablature cells could receive focus
but could not directly invoke a mobile software keyboard; and sticky application/editor chrome
consumed too much of a short landscape viewport. R4 preserves the R3 selection-safety model and
the owned document contract while refining those surfaces:

- At ordinary desktop widths, Pages is one compact toolbar containing its heading, horizontally
  scrollable selectors, New page, Duplicate, and Delete on one line. On mobile, Pages and New page
  form the first row, while the full-width selector strip and an accessible Page actions disclosure
  form the second. The disclosure contains Duplicate and Delete, all touch targets remain 44px,
  and switching pages after unsaved edits remains covered.
- Each tablature grid cell is now a controlled native text input with gridcell semantics,
  `inputmode=numeric`, a two-character limit, and a visible notation placeholder. Tapping the cell
  is therefore the user gesture that focuses the actual input instead of a button that subsequently
  tries to focus a separate field. Values `0`, `1`–`36`, empty, and desktop `x` map immediately to
  the existing structured Open, Fretted, Empty, and Muted states without changing event identity or
  serialization. Arrow navigation, multi-system layout, unified history, the visible contextual
  fret fallback, and Open/Mute/Clear controls remain available.
- The application shell receives a route marker only for `/prototype/workbook`. On that route the
  Instrument HUD topbar is non-sticky, so it scrolls away normally. In short mobile landscape
  layouts the Workbook formatting toolbar is also non-sticky and the document minimum height is
  reduced. Other application routes and the shared navigation model retain their existing chrome.
- A dedicated touch-enabled Pixel 7 landscape Playwright project verifies the non-sticky topbar and
  toolbar, direct two-digit cell editing, focused-cell visibility, and absence of page overflow.
  Portrait mobile projects continue to cover touch sizing, scrolling, chord editing, rich text,
  axe, and the complete Workbook interaction suite.

Browser automation proves that tapping the grid focuses the native input and that direct one- and
two-digit updates work in touch/mobile browser contexts. It cannot prove that a physical operating
system software keyboard appeared. The contextual fret input remains an explicit fallback, and
physical-device keyboard presentation remains part of user interactive review.

### Deferred Reading Mode and PDF direction

A later authorized ticket should render the same authoritative structured Workbook document in a
read-only mode showing page titles, text, lists, tablature, chord diagrams, annotations, and tuning,
without toolbars, fret controls, position actions, chord editors, JSON controls, or other editing
chrome. Reading Mode must not introduce a second document format.

Future PDF work should first evaluate a print-friendly Reading Mode plus browser Print / Save as
PDF. Planning must cover individual-page export, eventual full-workbook export, readable tablature
and chord diagrams, margins, page breaks, tuning/notation preservation, and removal of editing
controls. Dedicated PDF generation remains undecided and is not implemented by R4.

The previously recorded incomplete mobile navigation, global Instrument HUD behavior, and shared
mobile viewport ergonomics remain separate application-wide UX concerns. R4 changes topbar behavior
only on the isolated Workbook prototype route and does not alter canonical navigation.

No authentication, persistence, database, production, public-traffic, or global navigation change
is part of R4.

## JRN-001-R4 final arrow-navigation correction

User review accepts the Workbook usability, conditional on one final correction to the tablature
grid's vertical arrow direction. The grid renders conventional high-to-low tablature with String 1
above String 6, but the original key mapping moved `ArrowUp` toward a higher string number and
`ArrowDown` toward a lower one. The corrected mapping moves `ArrowUp` from String 6 toward String 1
and `ArrowDown` from String 1 toward String 6, stopping at the outermost strings without wrapping.
Left/right position navigation, including movement across rendered systems, is unchanged.

Focused browser coverage verifies the visual direction and boundaries under Standard and DADGAD
tunings. Existing regressions continue to cover direct fret entry, musical-block selection safety,
unified undo/redo, and owned JSON serialization. The editor technology remains Tiptap/ProseMirror;
persistence is not implemented, and production remains unchanged.

## Tiptap / ProseMirror assessment

### Evidence

- **Custom React nodes:** React node views support direct editing of structured musical attributes
  without separating music from the surrounding document.
- **Selection and focus:** toolbar commands preserve the document selection; musical blocks expose
  explicit return-to-document controls and predictable Escape behavior. Grid arrow navigation is
  implemented by the GuitaRPG node view.
- **Undo/redo:** musical attribute transactions and rich-text operations participate in one editor
  history and pass mixed browser interaction coverage.
- **Serialization:** an explicit adapter prevents Tiptap JSON from becoming the persistence format;
  deterministic mixed-document fixtures round trip without identity, order, content, or tuning loss.
- **Accessibility/mobile:** semantic controls, generated summaries, visible focus, 44px targets,
  numeric inputs, internal tablature scrolling, axe checks, and the required browser/viewport matrix
  are covered. A future production editor should deepen screen-reader testing of complex grid editing.
- **Maintenance/licensing:** `@tiptap/react`, `@tiptap/pm`, and `@tiptap/starter-kit` 3.32.0 are
  maintained open-source MIT packages. No paid collaboration or version-history package is included.
- **Bundle:** the production build succeeds with the prototype as a separately loaded client route.
  Exact route-level compressed transfer cost is not emitted by the current Next.js 16 build report
  and remains unmeasured; this should be budgeted before production navigation exposure.

### Recommendation

**ACCEPT WITH REMEDIATION.** Tiptap/ProseMirror is suitable for the GuitaRPG-owned structured-block
architecture and should remain the JRN-002 editor foundation if the interactive review passes.
Before production release, add deeper screen-reader/manual keyboard evidence, production-grade chord
barre/finger editing, and an explicit client-bundle budget. Nothing observed justifies implementing
Lexical or direct ProseMirror as a second framework.

## Known limitations

- State is deliberately memory-only and is lost on refresh unless exported.
- Rhythmic notation, measure editing, drag reordering, collaboration, and revision history are not
  implemented.
- Finger and barre fields are schema-compatible but have no production-grade editing controls.
- The chord `Clear position` action resets the string to the neutral muted state defined by the v1
  three-state chord contract.
- User visual and tactile acceptance remains outstanding; automation is not visual approval.
- A personal reusable chord library is a future product concept and is not implemented here.
- A reusable note bank for text or musical snippets is a future product concept and is not
  implemented here.
- Complete mobile application navigation remains deferred to a separately authorized ticket; R3
  records the deficiency without changing the shared shell.
- Reading Mode and print/PDF export are approved planning directions but remain unimplemented and
  require separately authorized scope.
