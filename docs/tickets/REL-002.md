# REL-002 — Core-Loop Integration Tests

**Status:** BLOCKED

**Phase:** 2 — Core Quest Loop

**Depends on:** QST-002, DIF-002, DIF-003, QST-003, SES-001, SES-002, EVD-002, HIST-001

## Objective

Prove that the completed Phase 2 subsystems form one production core loop across
runtime contracts, persistence, and the user-accessible application path.

## Terminal disposition

REL-002 is **BLOCKED** by a missing production application boundary. The generator
runtime can produce canonical Quests, but `/generate` still renders a
`FoundationPage`. No application call site invokes `generateQuickQuest` or
`generateCustomQuest`, maps and durably persists the generated Quest, or invokes
`startPracticeSession` for it.

The repository therefore does not currently provide the required user path:

`Generate → persisted Quest → started Session → practice → Result → History`

The mandatory application-flow audit reached an explicit REL-002 stop condition
before new integration tests were written. Adding a test-only writer, service-role
browser bridge, hard-coded fixture path, or the missing Generate feature inside this
ticket would falsely claim production integration and is prohibited.

## Audit evidence

- `app/generate/page.tsx` is a placeholder and contains no generator, persistence, or
  Session-entry integration.
- `generateQuickQuest` and `generateCustomQuest` have no application call sites.
- `toQuestPersistenceInput` has no application call site.
- `startPracticeSession` has no application call site.
- QST-003 explicitly deferred an application-level atomic multi-table Quest write
  adapter and the broad Generate/Session UI path.
- The downstream Session practice surface links to
  `/session/[sessionId]/complete`, and completion uses the production Result
  finalization repository.
- `/history` and `/history/[sessionId]` use the production owner-scoped history read
  model, including pending and finalized Results.
