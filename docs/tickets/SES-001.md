## Session semantics and runtime version

`SES_V1` represents exactly one attempt by one Player against one immutable durable
Quest. The Session owns runtime lifecycle only. A Quest may have multiple Sessions;
an ended Session is never reopened as a new attempt.

The public lifecycle is:

`START → ACTIVE → PAUSED → ACTIVE → ENDED`

Both ACTIVE and PAUSED may transition directly to ENDED. ENDED is terminal. There are
no CLEARED, FAILED, ABANDONED, PARTIAL, or MASTERED Session states.

## Runtime architecture

`lib/session/runtime.ts` provides versioned types, pure transition resolution, event-
history validation, Session/event consistency validation, and explicit-time active-
seconds derivation. It reads no clock and performs no I/O. `lib/session/repository.ts`
is the narrow owner-context adapter for the protected start/pause/resume/end RPCs; it
does not use a service credential or expose table mutation.

## Persistence and event model

Migration `20260928040000_ses_001_practice_session_runtime.sql` adds:

- `practice_sessions`: Player, Quest, SES_V1, ACTIVE/PAUSED/ENDED, authoritative start,
  optional terminal end, and creation timestamps
- `practice_session_events`: immutable ordered START/PAUSE/RESUME/END telemetry with a
  Session-scoped monotonic sequence and server timestamp

Events—not a mutable elapsed counter—are the timing authority. One transaction performs
each state change and event append.

## Trusted mutation, timestamps, and concurrency

Authenticated callers receive EXECUTE only on explicit lifecycle functions. The start
function derives ownership from `auth.uid()`, verifies the caller-owned Quest, and uses
one database timestamp for Session and START event. Transitions lock the Session row
`FOR UPDATE`, validate owner and expected state, assign the next sequence, update state,
and append the event with one `clock_timestamp()`. Concurrent duplicate transitions
therefore serialize and all but the first valid transition fail.

Ordinary authenticated clients receive SELECT only on the two tables. They cannot
directly insert Sessions/events, submit timestamps, update status/events, delete history,
or reorder events. Security-definer functions use an empty search path, explicit object
qualification, revoked default EXECUTE, and internal ownership checks.

## RLS, grants, and user classes

Both exposed tables have RLS enabled. Owner SELECT compares the immutable Player UUID
to trusted `auth.uid()`; event access is inherited through the owning Session. `anon`
has no grants. Supabase anonymous Auth and permanent users both operate as authenticated
owners and therefore use the same model. `service_role` retains explicit trusted table
access, but normal lifecycle calls require owner Auth context.

## Active-time derivation

Recorded active seconds are the floor of complete START/RESUME → PAUSE/END interval
durations. Paused intervals never count. The pure runtime can include an open interval
only when the caller supplies an explicit observation instant; it never reads wall time.
The database function derives closed authoritative intervals from ordered persisted
events.

This is app-session telemetry, not proof that guitar practice occurred. It is not
automatically XP-eligible time, and SES-001 adds no speculative idle detector.

## Quest historical integrity and account deletion

The Session Quest FK uses `ON DELETE CASCADE` so trusted Auth-account deletion can remove
the complete Player graph. A guarded Quest `BEFORE DELETE` trigger rejects an ordinary
authenticated deletion whenever Session history exists. During trusted account deletion
there is no authenticated caller identity, so the existing Auth → Quest cascade and the
Session's Auth/Quest cascades may complete.

Tests cover both required behaviors. This deliberately avoids a literal Session → Quest
`ON DELETE RESTRICT`, whose immediate enforcement could prevent the accepted DATA-001
account-deletion cascade. Direct trusted correction remains outside ordinary client
authority.

## QST, EVD, PROG, and SES-002 boundaries

Sessions reference QST-002's durable immutable Quest; ending a Session never mutates its
resolved snapshot or DIF_V1 profile. The QST-003 application Quest-write adapter gap is
unchanged and does not block Session lifecycle tests against durable Quest fixtures.

SES-001 creates no Result, criterion result, evidence record, verification conclusion,
reflection, personal-difficulty snapshot, XP, Skill evidence, proficiency, readiness,
Attribute, Character Level, recommendation, audio, timer UI, metronome, rep counter, or
practice-reference control. EVD-002, Phase 3, and SES-002 retain those responsibilities.

## DORIAN CROSSROADS acceptance path

The database acceptance fixture persists a durable DORIAN-derived Quest, starts an
ACTIVE SES_V1 attempt, records START/PAUSE/RESUME/END in sequence, ends terminally, and

proves the Quest remains unchanged, ordinary deletion is blocked, multiple attempts are
allowed, and account deletion removes both attempted Quest and Session history. No
Result, XP, or proficiency mutation is created.
