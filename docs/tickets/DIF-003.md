## Objective

Implement a pure, deterministic, versioned resolver that compares an accepted DIF_V1
absolute Quest-demand snapshot with relevant Player Skill-state and Context-novelty
snapshots without mutating Player state.

## Persistence boundary

The resolver is runtime-only. PLY-002 lacks generalized Player×Context exposure, so
Context novelty is an explicit typed snapshot supplied by a future adapter. No broad
Context/Constraint exposure model, evaluation-history table, or migration is added.

## Resolver architecture

`lib/difficulty/personal-types.ts` defines the PLY-002-compatible input and auditable
snapshot output. `lib/difficulty/personal-v1.ts` validates the explicit snapshot and
then performs:

1. accepted DIF_V1 absolute-demand ingestion
2. Primary and supporting Skill-role resolution from the Quest
3. primary/domain and supporting/domain capability-gap calculation
4. baseline personal-Level mapping
5. bounded readiness, Context-novelty, and supporting-bottleneck interpretation
6. separate status and uncertainty resolution
7. immutable snapshot/rationale output

The public pure API is `resolvePlayerRelativeDifficulty(input)`. It performs no I/O,
uses no wall clock, and returns no recommendation or mutation instruction.

## Input snapshot

The input requires the resolved Quest, its already-computed DIF_V1 profile, a unique
set of PLY-002-compatible Skill snapshots, explicit Context novelty, caller-supplied
`evaluated_at`, and a Player-state snapshot version. Rated states require a consistent
0–100 proficiency and visible Level; corrupt, duplicate, unsupported, or missing
Primary state fails clearly.

Context novelty is `LOW`, `MODERATE`, `HIGH`, or `UNKNOWN`, with explicit context keys
and snapshot provenance. This interface honestly supports the Phase 0 novelty fixture
without inventing unavailable generalized Context persistence.

## Capability-gap and personal-Level model

The Primary Skill is dominant. Its demand coordinate is:

`round(0.65 × primary-domain dimension + 0.35 × absolute overall demand)`

The model gap is `demand coordinate - persisted proficiency score`. The versioned
mapping is:

- gap ≤ -50 → I / Very Comfortable
- gap -49 through -20 → II / Comfortable
- gap -19 through 15 → III / Target Challenge
- gap 16 through 35 → IV / Stretch
- gap > 35 → V / Overreach

These are model coordinates, not empirical percentages. Output remains the semantic
I–V band.

Supporting Skills map through their canonical Quest role and Domain to the relevant
absolute dimension. Missing required technique, UNRATED support, or a supporting gap
of at least 20 is an explainable bottleneck. Primary capability remains the baseline;
support cannot make a Quest easier.

## Status rules

- `UNKNOWN`: Primary Skill is UNRATED; personal Level is always null.
- `PROVISIONAL`: Primary is ESTIMATED, supporting coverage is missing/estimated/
  unrated, or Context novelty/exposure is HIGH/UNKNOWN.
- `RESOLVED`: Primary is ESTABLISHED with sufficient relevant coverage. Readiness LOW
  can still be RESOLVED because it changes current challenge, not evidence certainty.

## Uncertainty rules

- `HIGH`: Primary UNRATED, ESTIMATED below confidence 40, or supporting capability is
  missing/unrated/weakly estimated.
- `MODERATE`: informed estimate, established capability with incomplete context/
  readiness certainty, or high novelty.
- `LOW`: established Primary at confidence 75+, sufficiently established supports,
  known readiness, and LOW novelty.

Confidence never changes the gap, baseline Level, or effective demonstrated
capability.

## Modifiers and composition

- LOW readiness: `READINESS +1`; HIGH/MODERATE add nothing; UNKNOWN changes
  uncertainty only.
- HIGH Context novelty: `CONTEXT_NOVELTY +1` and PROVISIONAL; UNKNOWN changes
  uncertainty/status without fabricating capability loss.
- severe supporting mismatch: `SUPPORTING_SKILL_BOTTLENECK +1`.

Each modifier is individually capped at +1. DIF_PERSONAL_V1 composes simultaneous
modifiers with a total +1-band cap, preventing uncontrolled +3 inflation. Final Level
is bounded I–V. Every modifier explicitly states `changes_proficiency: false`.

## Versioning and historical integrity

The evaluation retains absolute model `DIF_V1`, resolver `DIF_PERSONAL_V1`, evaluation
time, Quest reference, Player-state version, exact Skill/Context snapshots, capability
gaps, modifiers, and rationale. A future persistence ticket can store this immutable
shape without recomputing historical evaluations. DIF-003 itself adds no persistence.
