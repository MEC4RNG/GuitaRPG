## Implementation design

### Decision

QST-002 persists **only player-owned, resolved Quest instances**. The Phase 0
fixtures remain contract/test data: they demonstrate the public resolved Quest
shape, but do not imply a global template or fixture table. Generator/template
storage is deferred to QST-003 or a later authorized editorial-data ticket.

The persistence model is deliberately hybrid:

- `quests` carries owner, immutable instance identity, version/type/origin,
  primary Domain and primary Skill references, and the complete validated
  schema-v1 resolved snapshot.
- child tables retain the canonical IDs and ordering needed for relational
  integrity/querying: non-primary Skill roles, Concepts, Contexts,
  Constraints, and Objective criteria.
- parameterized/compound containers remain constrained JSONB on `quests` or
  their child rows. They are validated by the TypeScript schema-v1 parser;
  they are not opaque application blobs.

The validated `resolved_snapshot` is authoritative for historical
reconstruction of the practice plan. It includes the resolved names, slugs,
parameters, and schema version that were presented at creation time. Canonical
foreign keys are authoritative for relationships and current taxonomy joins;
historical displays must use the snapshot rather than silently substituting
renamed taxonomy labels.

### Ownership, mutation, and lifecycle

Every Quest belongs to one `auth.users` Player (`on delete cascade`). RLS grants
the authenticated owner select/insert/delete only; there is no client UPDATE
grant. This makes the resolved plan append-only. A player may delete an
unattempted Quest now; a future Session/Result table must use `on delete
restrict` when it references a Quest so historical attempted work cannot be
removed. Revisions and `supersedes_quest_id` are deferred: materially changed
work receives a new Quest identity.

No system-owned Quest, generator, result, evidence, Session, XP, progression,
or recommendation table is introduced.

### Database constraints and runtime boundary

PostgreSQL enforces relational references/kinds, schema version, public enum
values, exactly one non-null primary Skill, no duplicate non-primary Skills,
role cardinalities, Concepts/Constraints/criteria minimums, normal constraint
maximum, criterion operators/scalar JSON values, and the no-mastery/no-fixed-
XP/no-progression boundaries. Deferred constraint triggers make cross-row
composition checks transaction-safe.

The TypeScript parser is the semantic boundary for the public object: it
validates every Phase 0 fixture and rejects malformed nested fields, duplicate
roles including a primary collision, invalid parameter/context shapes,
unsupported versions, invalid verification profiles, and any embedded attempt,
Result, reflection, XP, or progression data. The persistence mapper derives
the relational rows from that parsed object and retains the canonical snapshot.

### Blocking authority conflict

QST-001 requires canonical Constraint Definitions for each resolved Constraint
in its accepted fixtures. The checked-in/staging TAX-003 taxonomy contains only
these Constraint slugs: `adjacent_strings_only`, `change_strings_each_bar`,
`double_stop_texture`, `even_strings_only`, `high_strings_only`,
`low_strings_only`, `non_adjacent_strings_only`, `odd_strings_only`,
`single_string_only`, `single_string_per_measure`, `skip_every_other_string`,
`skip_two_strings`, and `string_count`.

It contains none of the QST-001 fixture definitions `string_set`,
`fret_range`, or `target_tempo`. Creating those entities in QST-002 would
silently expand TAX-003 authority, which is prohibited. The QST-002 migration
was applied before this fixture-to-taxonomy gap was exposed by the staging
pgTAP test; it is retained as a forward-only, non-destructive schema change.
No migration-history repair was used.

**Required next action:** explicitly authorize a taxonomy remediation to add or
otherwise contractually reconcile those required canonical Constraint
Definitions, then resume QST-002 validation. Do not begin DIF-002.
