## Model architecture

`lib/difficulty/` separates the model into:

1. `features.ts` — validates through the QST-002 parser and extracts only resolved
   Quest semantics
2. `dif-v1.ts` — applies explicit applicability and additive/interaction scoring rules
3. `types.ts` — fixes the seven-dimension, basis, model-version, and source output shape
4. overall aggregation — applies a Quest-Type bottleneck lift to the applicable-
   dimension mean

The public entry point is `evaluateAbsoluteQuestDemand(input)`. It always parses the
input as a schema-v1 resolved Quest before evaluation.

## Feature extraction strategy

Features include Quest Type, primary Domain, Skill roles/domains, Concepts, objective
kind/criteria, meter, canonical Constraint slugs and resolved parameters, target BPM,
time window, string traversal, fret span, and required output count. Identity, title,
verification, rewards, metadata, and declared illustrative demand do not score.

Canonical semantic classification remains private versioned DIF_V1 configuration. No
difficulty field was added to taxonomy and no Skill owns an inherent Level.

## Applicability

- TECHNIQUE requires physical execution semantics.
- FRETBOARD requires navigation, traversal, or constrained physical material.
- THEORY requires conceptual/construction/application semantics.
- RHYTHM requires an explicit rhythmic grid, Concept, or generative rhythmic output.
- CREATIVE requires a generative objective/type.
- TEMPO requires target pace, time pressure, prompt pacing, or pulse reinterpretation.
- CONSTRAINT is applicable for the QST-001 requirement of one to three resolved
  restrictions.

Inapplicable dimensions always contain `applicable: false`, `score: null`, and
`level: null`; they still carry a stable explanatory basis code.

## Scoring design

Each applicable dimension sums inspectable feature contributions and bounded
interaction terms, rounds to an integer model coordinate, and defensively bounds the
result to 0–100. Level is derived only through the accepted bands: I 0–19, II 20–39,
III 40–59, IV 60–79, and V 80–100.

Constraint demand accounts for restriction kind, count, threshold magnitude, and
bounded simultaneous/execution/creative interactions rather than raw count alone.
Tempo combines pace with execution/subdivision/traversal context; the same BPM is not
assigned one universal demand.

## Overall aggregation

DIF_V1 computes the applicable-dimension mean, then lifts it toward the highest
meaningful demand using a documented Quest-Type bottleneck coefficient:

`round(mean + quest_type_coefficient × (maximum - mean) + bounded_load_term)`

Coefficients are TECHNIQUE 0.70, KNOWLEDGE 0.85, EXPLORATION 0.92, PERFORMANCE
0.82, and CREATIVE 0.45. A six-point bounded prompt-set load applies to Knowledge
identification with at least ten prompts. N/A dimensions never participate. This is
neither a simple maximum nor an unweighted average and preserves the accepted severe
metric-modulation bottleneck.

## Monotonicity and invariants

Controlled-variant tests prove non-decreasing target-BPM, reduced-response-window,
added-constraint, fret-span, string-traversal, and creative-output behavior. Tests also
prove exact score-band mapping, bottleneck preservation, N/A exclusion, identity/slug
invariance, verification/reward independence, deterministic output, and 24/24 QST
fixture structural coverage.

## Boundaries

- The evaluator consumes only a validated resolved Quest.
- It does not accept or inspect Player state, readiness, confidence, XP, Character
  Level, evidence history, or onboarding background.
- It produces a computed immutable snapshot suitable for later Quest persistence.
- Personal status, capacity, uncertainty, and modifiers remain deferred to DIF-003.
- No migration or Player-owned persistence is expected.

The QST-002 `difficulty_profile` JSONB and immutable resolved snapshot already support
the complete profile and historical model identity. Later recalibration requires a new
model version; DIF_V1 snapshots must not be silently recomputed. No migration was added.

## DIF-003 deferrals

Player capacity, Skill assessment/proficiency, readiness, confidence, context exposure,
uncertainty, UNKNOWN/PROVISIONAL/RESOLVED status, personal Level, supporting-Skill
bottlenecks against Player state, and recommendation use remain explicitly deferred.
